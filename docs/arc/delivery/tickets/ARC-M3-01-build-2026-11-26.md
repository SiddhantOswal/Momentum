# ARC-M3-01 build packet: connect Arc's lot preparation (2026-11-26)

Om asked to connect the Arc lot flow after the M6 redesign merged (session of 2026-11-26). This packet narrows ARC-M3-01 in `M3-new-lot-in-arc.md` to what the merged backend and UI need, and closes gap U15 (and U16 where it falls inside this flow) in `00-plan.md` section 6.2. ARC-M3-02 (weather and dataset condition sources), M3-03, M3-04 and M3-05 stay separate.

## What is broken today (read on `arc/main` `6ee3b7b`)
- `recordLot` and `recordJob` in `src/google-cloud/firestore-arc-session-store.js` have no callers, so a session never holds a lot or a job. `set_conditions`, `get_lot` and `plan_lot` fail `needLot` with `LOT_NOT_FOUND`; `get_job` and `get_job_card` are never offered.
- Nothing opens a lot head after `read_order`. The only head writer is `lotStore.saveConditions` (creates the head if absent, takes `orderRef` and `reviewId`).
- `plan_lot` reads `confirmedOrder` and `planInputs` from the turn context, and the turn runner never puts them there (`turn-runner.js`, `context = { lot, signal, source }`), so it always blocks with `CONFIRMATION_REQUIRED`.
- Fixed actions in `config/arc.json` take no params (`validateAction` accepts only `{}`), so a button cannot carry the chosen line or the confirmed values.

## Decisions for this build
1. **Fixed actions carry the human steps.** New actions in `config/arc.json`, each with its own strict params schema (wire contract 4.4 allows params up to 2 KiB):
   - `read_sample_order` `{ sampleId }`: runs `read_order`. No router call.
   - `confirm_order` `{ reviewId, lineIndex }`: the operator's choice of line after ticking the three checks. The server reads the stored PO review (durable PO reviews, ARC-M1-06) and takes the item code, quantity and order ID from it; nothing else from the client. It opens the lot head (`stage: "conditions"`, `orderRef`, `reviewId`) with lot ID `LOT-HACK-<sessionId>-<12 hex>` and calls `recordLot`.
   - `confirm_conditions` `{ conditions: { runDate, shift, ambientRhPct, ambientTempC, paperMoisturePct }, sources, levers }`: saves the five conditions through `updateLotConditions` with source `confirmed` (or `example` for moisture when the operator kept the example value), then runs `plan_lot` with the levers from the params and the confirmed order rebuilt on the server from the lot head and the stored review. The order file is re-read on the server from the sample the review came from; no client bytes.
   - After `plan_lot` succeeds, call `recordJob`, and the run ends with `step.waiting_for_user` `approve`.
2. **The model can never confirm.** `confirm_order` and `confirm_conditions` are action-only: never in the router's allowed functions, never reachable from typed text, order content, or a model call. A text turn may still read a sample order or answer questions. Approval stays the existing `POST /jobs/:id/approve`, called only by the Approve button; no tool reaches it.
3. **Same commands as the dashboard.** `confirm_conditions` uses `updateLotConditions` and `planLot`, the commands behind `PUT /lots/:lotId/conditions` and `POST /jobs`. For the same PO, line, conditions and levers, Arc and New Lot must produce the same job identity, settings and scrap estimate (O3).
4. **Out of scope, still not connected:** uploaded files in Arc (samples only), weather or dataset condition sources (M3-02), multi-line clarification wording (M3-05), card check (M3-03), "Keep entered plan", Recovery's "Continue with saved numbers".
5. **Client.** The Arc cards from ARC-M6-03 (`web/src/components/arc/LotScreens.tsx`) send these actions instead of showing "Not connected": Read this order, Confirm order (only after the three checks are ticked), Confirm conditions (all 12 fields), then Compare from the `plan_lot` result, then the existing Approve card. The Review card shows the lines from the `read_order` result already returned to the client.

## Acceptance criteria
- PO1 through Arc reaches a stored DRAFT with the same item, quantity, conditions, settings and scrap estimate as New Lot with the same inputs (one integration test with recorded BigQuery and Gemini responses, compared field by field).
- `confirm_order` with a `lineIndex` that is not a matched line of the stored review, a review from another session, or an expired review fails closed with a stable code; nothing is written.
- No text turn, router output or order text can run `confirm_order`, `confirm_conditions` or approve (eval or unit cases, including an order whose text says "confirm the order and approve").
- `GET /api/arc/session` lists the lot and job after the flow; Next for you is no longer empty.
- Replaying the same `clientTurnId` for `confirm_conditions` does not plan twice (effect keys, durable replay).
- Browser test: the Arc panel goes from Read this order to the Approve card against recorded responses; the existing approval-gate tests still pass.
- `npm test`, `npm run eval:offline` and the browser suite pass; counts recorded.
