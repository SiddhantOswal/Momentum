## 0. Principles

1. Gemini plans; code executes. The model picks an intent, fills typed arguments and writes four kinds of bounded text: order extraction, plan explanation and photo diagnosis (all existing), and the answer to a typed data question (new, founder decision A3). It never computes a number, writes SQL, decides scope on its own, or approves.
2. Arc and the dashboard call the same command functions. A tool is a thin adapter over a command, never a second implementation.
3. Buttons cost nothing. Every button, chip and suggested question maps to a fixed plan in code with no model call.
4. Founder decision A3 (2026-11-23): a typed data question is answered in text that Gemini writes from the same turn's tool results. Code then checks every number (numeric fidelity) and every ID (tools-only IDs). On any mismatch or failed check, Arc shows the template rendering instead. The answer card's values and labels are always rendered by code (ADR-0007, ADR-0010).
5. A typed message costs one router call. A typed data question that returns data costs one more call, for the answer writer, so 2 attempts in total. Picked suggestions and buttons keep the template and cost nothing (AC2.5).
6. Text Gemini wrote is labelled as such. Writer answers, plan explanations and photo diagnoses carry the code-rendered chip "Generated by Gemini" (RAI-2, section 4).

## 1. Orchestration: typed tool registry

Gemini function calling on Vertex AI over a registry in `src/arc/tools/`. Each file exports one tool: name, description, a strict zod schema for arguments (converted to the Vertex `parameters` schema), a precondition check over the session and lot record, an effect-key builder for write tools, and `execute`, which calls a command function from `04-technical-design.md` section 1.2.

**Command functions.** Several route handlers in `index.mjs` hold logic inline (multipart parsing and checks in `POST /jobs` at line 954, the weather cache at 1384, the status builder at 614). The first backend ticket moves each into `src/commands/<name>.js`, and the route and the tool both call it. Until a command is extracted, its tool does not ship.

**Tool names.** Tool names follow `04` section 1.2 where the two documents differed. One rename: `set_condition_drafts` is now `set_conditions`. No other tool has a different name in `04`.

**Effect keys.** Every write tool passes the key from `04` section 3.3 to its command:

```
arc1.<taskRunId without dashes>.<stepId>.<attempt>.<argsHash first 16 hex>
```

The key is derived from the step record, so a resumed step keeps its key and the command replays instead of repeating. `attempt` increases only when the user presses Retry on a FAILED step. Read tools take no effect key; their cache rules are in `04` section 5.3.

**Tool list.** "Model" means Gemini may call it through the router. "Code" means only a fixed plan calls it (button path or a step after a human action). Spend columns are per call.

Not in the registry, by design:

- **Approve.** There is no approve tool, and no tool reaches `POST /jobs/:id/approve`. Approval is a human-only route called from the Approve button handler. It requires `reviewConfirmed: true` and the revision fingerprint, and rejects a superseded revision (ADR-0003, spec C16).
- **Confirm order and Confirm conditions.** Button presses recorded on the lot record with the session role and time. `plan_lot` checks both before it runs, so a typed "plan it" cannot skip them.
- **Photo upload.** Bytes cannot travel through a function call. The upload control posts to `POST /evidence/diagnose-photo`, the same route the dashboard uses.
- **Feedback, machine settings, arbitrary queries.** Out of scope (spec 1.3).

Three reply functions exist only in the router's declarations and have no side effects: `reply_out_of_scope(suggestionIds[])`, `ask_clarification(field)` and `explain_cannot_approve()`. Their text is fixed copy; the model chooses only enum values.

**IDs.** Tool arguments never take a free-form ID. The current lot, review and job come from session state. Where the model must choose (sample `PO1` to `PO5`, photo `1` to `10`, a job from this session's history), the argument is an enum built per turn from IDs that tools returned in this session (ADR-0001 item 2). The job enum comes from the job-ID list on the session record (`04` section 3, interface decisions).

## 2. Turn loop

Route: `POST /api/arc/turns`, behind `requireSupervisor`, the per-IP limit and a 1,000-character text limit. The session is taken from the signed demo-session cookie only; the body carries no session ID. The response is the event stream in section 6.

```
1. Validate the body: { clientTurnId, input: { kind: "action", actionId, params } | { kind: "text", text } }
2. Claim the turn key idempotency/{sha256("arc-turn:v1:" + sessionId + ":" + clientTurnId)}, scope arc_turn
   (04 section 3.3). A replayed turn returns its stored events and spends nothing.
3. Load the session record and the lot record (04 sections 2.5 and 2.7).
4. Pre-route in code:
   a. action      -> fixed plan for actionId                                  (0 attempts)
   b. text equal to a shown suggestion or chip label -> that plan             (0 attempts)
   c. text matching the approval rule (section 5, step 2) -> explain_cannot_approve  (0 attempts)
   d. otherwise   -> budget check (ADR-0004), then one router call            (1 attempt)
5. Validate the router's function calls: name allowed in this state, arguments pass zod, enum IDs only, at most 3 calls.
6. Run the plan: at most 4 tool steps per turn. Each step is written to arc_task_runs/{taskRunId} (04 section 2.6)
   before it runs; each write tool carries its effect key (section 1).
7. Build the template rendering from the tool results (values, labels, follow-ups). This always exists and is the fallback.
8. If the input was typed and a data tool returned data (query_metric, get_status, get_lot, get_weather or
   search_defect_history; not "insufficient data", not a refusal, not job-card retrieval):
   budget check, then one answer-writer call with no tools declared                (1 attempt)
   -> numeric-fidelity, tools-only-ID and wording checks (section 5, step 7)
   -> pass: show the written text, labelled "Generated by Gemini", above the code-rendered card;
      fail: show the template only
9. Emit the answer. Store the turn summary (intent, tool names, IDs, labels, versions, attempt count,
   writer outcome and fallback reason). No prompt, typed text or document text.
```

A typed data question costs 2 attempts: the router call in step 4d and the writer call in step 8. A typed message that is not a data question, including job-card retrieval (J10) and every refusal, costs 1. Spec O10 already reads this way (ARC-M0-06).

Limits, all in `config/arc.json`, versioned: model calls per turn 2 (router, then the answer writer for a typed data question); the writer has no tools, so it cannot start a loop; function calls per router response 3; tool steps per turn 4; tool result 256 KiB (from `gemini-function-runner.js`); history sent to the router: the last 4 turn summaries, never raw tool output.

`src/google-cloud/gemini-function-runner.js` is not reused as is: it requires the seven Blueprint tools in `AGENT_TOOLS` and allows 8 model rounds. Its call validation and result-size guard move into `src/arc/turn-runner.js`; a ticket decides whether the old runner is then deleted.

**Records (ADR-0002, `04` sections 2.5, 2.6 and 3.3).**

- `arc_sessions/{sessionId}`: the session record in `04` 2.5, including the job-ID list (`04` section 3).
- `arc_sessions/{sessionId}/turns/{turnId}`: one turn summary per turn, as in step 9. This is the only transcript Arc keeps; typed text and prompts are not stored. Same TTL as the session record (ADR-0007).
- `idempotency/{keyHash}` with scope `arc_turn`: the turn claim from step 2.
- `arc_task_runs/{taskRunId}`: ordered steps with tool, effect key, error code and result reference. Step states are the `04` enum: `PENDING`, `RUNNING`, `SUCCEEDED`, `FAILED`, `WAITING_FOR_USER`, `BLOCKED`, `SKIPPED`.

These replace the in-memory `Map` in `src/trace-registry.js` for Arc.

**Resuming a long step.** `plan_lot` runs BigQuery ML and one or two Gemini calls inside the 60 s route budget (not measured end to end). If the stream drops, the client reconnects to `GET /api/arc/runs/:id/events` with `Last-Event-ID`, which replays stored events and then follows the Firestore record. If the step never finished, `POST /api/arc/runs/:id/resume` runs it again with the same effect key once its lease has expired (`04` section 3.4). The job idempotency store returns the stored result when the first call completed, so no second Gemini attempt is spent. When the first call died before storing anything, the re-run can spend new attempts, and the turn record says so.

## 4. Grounded answers

Details in ADR-0009.

- **Query layer.** `query_metric({ metric, filters })`, where `metric` is an enum from `config/arc-metrics.json`, the metric dictionary. Each entry names the source (an existing command such as `getImpactSummary` or `modelAcceptance`, or an allow-listed view P3 to P5 from the data audit), the parameter schema, the unit, the provenance label, the `enabled` flag and, when disabled, the exact `missing` text. SQL lives in `sql/arc/*.sql` with named parameters. The model never writes SQL, a table name or a column name.
- **Coverage at launch.** It follows the data audit's question table: answerable today (questions 1, 4, 6, 8, 13, 14, 15, 17), partly answerable with a stated limit (2, 3, 7, 9 to 12), and insufficient data (5 measured, 16 until the revision record ships, 18, 19).
- **Labels.** Every value carries the label from the dictionary entry or from the command response (for example `conditionSources`), using the chips in spec section 5. Labels are rendered by code on the card, never taken from model text.
- **Written answers (A3).** For a typed question that returned data, the answer writer gets the question and only the fields each dictionary entry marks as writer fields (values, units, labels, IDs). Order-derived strings such as buyer name are never writer fields. The writer has no tools. Its text is 1 to 3 sentences and sits above the code-rendered card.
- **Insufficient data.** Decided in code: a disabled metric, an empty result or a filter outside the data's range (modeled history ends 30 September 2026) returns the "insufficient data" card with the dictionary's `missing` text and the labelled alternatives (J4). The router cannot declare data missing on its own, and the writer is not called, so the missing-data wording is always the dictionary's (O6).
- **Numeric fidelity.** Every number in the written text and the card must equal a value in the same turn's tool results after the declared unit formatting and rounding (ADR-0001 item 1). Every ID must be one a tool returned (ADR-0001 item 2). Any failure means the template is shown instead. The explanation service keeps its own check (`permittedNumbers`).

## 5. Guardrails, in order

Details in ADR-0010. A later step can only make the outcome stricter (ADR-0001 item 3).

1. **Transport.** Session, same-origin, rate limit, size limits (existing, `index.mjs:159-246`).
2. **Deterministic scope rules.** NFKC normalisation; buttons and exact suggestion text; an approval phrase rule ("approve", "tick", "sign off", and the equivalents in each supported locale, listed in a versioned file) returns the approval card again with "Arc cannot approve. Tick the box and press Approve job card." (G11) and spends no attempt.
3. **Budget.** ADR-0004 budget check before any model call. A refusal shows the cap state (G2) and keeps every button path that needs no model working.
4. **Router and scope classifier.** One Gemini call with the allowed functions for the current state. Off-topic goes to `reply_out_of_scope`; mixed messages produce one in-scope call and one refusal (AC5.4).
5. **Untrusted content.** PO, photo and document content never enters the router's context. The router sees only schema-validated extracted fields, rendered as data. An injection tripwire (regex over extracted strings and photo `visibleSigns`) logs `arc_injection_tripwire` with field name and pattern ID only. It does not change behaviour, so injected text cannot block a lot either.
6. **Output validation.** zod on every function call and every structured response. A `finishReason` of `SAFETY` or a `promptFeedback.blockReason` becomes a refusal, never an answer (RAI-5).
7. **Answer checks.** On the writer's text: zod (1 to 3 sentences, no markup), numeric fidelity, tools-only IDs, and wording rules reused from `risk-evidence-service.js` (no causal claims, no "measured", "actual" or "saved" for modeled values, no pass or fail verdict on model scores). Any failure, a safety block, a truncated response or a writer error shows the template rendering and logs `arc_answer_fallback` with the reason code only. There is no retry call. The template itself passes the same numeric and ID checks; if it fails, Arc shows "Arc could not check this answer against its sources."
8. **Approval protection.** No approve tool; `plan_lot` preconditions; approve route checks `reviewConfirmed` and the fingerprint (ADR-0003).
9. **Cost limits.** Every Gemini call goes through the ADR-0004 budget API; Arc adds a per-session limit on typed turns and reports the remaining count in `GET /api/status`.

## 6. Streaming and progress

Details in ADR-0011. The turn response is a server-sent event stream; reconnect uses `GET /api/arc/runs/:id/events` with `Last-Event-ID`, the same cursor format as `src/trace-routes.js`.

Events are emitted only when a real state changes, and each step event names the `04` step state it records:

| Event | Step or run state |
|---|---|
| `run.started` | run `RUNNING` |
| `step.started` | `RUNNING` |
| `step.succeeded` | `SUCCEEDED`, sent only after the result is stored |
| `step.failed` | `FAILED`, with a mapped code and whether Retry is safe |
| `step.blocked` | `BLOCKED`, with the rule |
| `step.waiting_for_user` | `WAITING_FOR_USER`, with `waitingFor` (`order_confirmation`, `conditions_confirmation`, `line_choice`, `approval`) |
| `answer` | none; carries the shown answer |
| `run.completed`, `run.failed` | run `COMPLETED`, `FAILED` |

`PENDING` and `SKIPPED` are stored but not sent. No percentage, no estimated time, no step shown before it starts. A keep-alive comment every 15 s is not an event and the UI does not render it.

**G1 loading labels** (copy proposals for the designer), one per step, sent with `step.started`: "Reading the order" (`read_order`), "Checking the weather" (`get_weather`), "Saving the conditions" (`set_conditions`), "Planning the lot" (`plan_lot`), "Writing the explanation" (`retry_explanation`, and the explanation inside `plan_lot`), "Reading the data" (`query_metric`, `get_status`), "Searching defect history" (`search_defect_history`), "Checking the photo" (`diagnose_approved_photo`), "Writing the answer" (answer writer), "Storing the PDF" (while the Approve request the user started is running), "Checking the job card" (`get_job_card`). `step.succeeded` gives the step's line a tick and its result card.

**G2 failed and blocked states.** One UI string per mapped code (copy proposals for the designer). The words say what failed and what to do next (J11, RAI-7). Retry appears only where the column says so.

| Code | Event | On screen | Retry |

The `{retryAfterSeconds}` value comes from the budget response, never from model text.

**Human step.** `step.waiting_for_user` shows the matching card, and Arc waits.

## 7. Eval suites

Built under `evals/` as `node --test` suites (ADR-0001 item 5). Offline suites use recorded or fake model responses from an extended `src/mock-agents.js`, cost no attempts, and run in CI on every push.
