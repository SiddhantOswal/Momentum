## What the evidence establishes

1. **Identity and version.** Each model has exactly 1 training run. Each BigQuery model records its Vertex link (`trainingRuns[0].vertexAiModelId`, `vertexAiModelVersion = 1`). Each Vertex version was created during that model's training job.
2. **Training provenance.** All five came from one script job, `bqjob_r4cfdf43fbdc1dad1_000001a12c5223a4_1` (11 Oct 2026, 18:55–19:35 UTC). There is one child `CREATE_MODEL` job per model, with a SHA-256 of its exact SQL. Each BigQuery model's creation time equals its child job's end time.
3. **Data and windows.**
   - Source table: `prepagent-hack.prepagent.lots`.
   - Training window: 1 Oct 2024 to 31 Aug 2026, **5,131 lots**, enforced by the SQL filter `run_date < DATE '2026-09-01'`.
   - Holdout: 1–30 Sep 2026, **219 lots**.
   - Both windows are fingerprinted, and no TEST rows are present.
4. **Split.** RANDOM, with an evaluation fraction of 0.2, inside the training window. **The exact internal-split counts are not recoverable**: BigQuery has deleted the temporary split tables, which returned "not found" on 16 Oct. No estimated count is given.
5. **No target leakage.** The other defects' rates, totals, cost, primary defect, IDs, date and item code are excluded from every model, as the hashed training SQL shows.
6. **Holdout integrity.** The holdout was excluded from training. It was not used for tuning (default options) or for setting thresholds (those were fixed before 16 Oct). It is also used by the impact simulation, which is a separate use.

## Data provenance

The training table is **modelled production history**. It was generated by `generator.ts` (seed 20261010) from the plant's real 117-item master, real paper costs (Rs 55/kg for 180 GSM, Rs 52/kg for 160 GSM) and the defect rules described by the plant's operators. It is not a set of recorded plant measurements. The metrics therefore measure how well the models learn the plant's modelled behaviour, not measured factory accuracy. The generator's noise level was calibrated during data preparation. **Next (finals):** validate on 50–100 real lots digitised from the plant's production records.

## Quality and limitations

- **R² is a limited metric here.** Scrap rates are small, skewed percentages, so a few bad lots dominate R². MAE (in percentage points of scrap) is the more practical measure: 0.13–0.30 internally and 0.14–0.54 on the holdout.
- **The unseen monsoon month is harder.** Warp, delam and strength lose 0.17–0.20 R² on September. Rates and spread are higher there, and bad paper batches cluster.
- **Crack has no skill within the monsoon month** (holdout R² −0.01). Humidity is uniformly high in September, so crack rates barely vary. The model is useful mainly across seasons. The UI shows crack as **low confidence in monsoon**. It is about 0.7 percentage points of scrap, so recommendations barely depend on it.
- **Strength is a weak model** (internal R² 0.47). It is a small share of scrap.
- **customer_id** has small, non-causal importance (largest in print: gain 8.3 over 3 splits). This is accepted for the prototype. Retraining without it is future work.
- **Out of distribution:** box types or conditions outside the item master and the modelled seasons are not supported. Unknown items are blocked in the app.
- Feature importance shows association, not causation.
